# 0095. Перевод строки в наборе - Shift+Enter, сообщение людям сверяется глазами до Enter

- **Статус:** Принято
- **Дата:** 2026-11-19

Частично заменяет [0044](0044-human-hand-in-browser.md) (многострочный текст в Browser больше не
вставляется одним куском) и [0058](0058-computer-use-windows.md) (перевод строки - не Return).

## Контекст

Агенты пишут людям от имени человека через оба коннектора, которые печатают: Browser (`type` и
`fill` в Chrome человека) и Computer Use (`type` настоящей клавиатурой). Это WhatsApp Web, Telegram,
Slack, Teams. В них Enter отправляет сообщение, а строку переносит Shift+Enter.

Как было:

- Browser: текст с `\n` уходил в поле одним `Input.insertText`. Что редактор сайта сделает с
  переводами строк, зависело от него: абзацы склеивались или вели себя непредсказуемо. С `slowly`
  перевод строки был клавишей Enter, то есть отправкой.
- Computer Use: перевод строки был клавишей Return, и ADR 0058 записал это намеренно: «модель
  рассчитывает, что Return в мессенджере отправляет». На деле это значит, что многострочное
  сообщение уходит по первой строке.
- Пояснения серверов об этом молчали.

Итог: агенты избегали переводов строк и слали сообщения одной строкой. Владелец пожаловался:
нумерованный список вопросов ушёл одним абзацем. Он попросил гарантию в самих инструментах, а не
надежду на промпт, и добавил второе требование: каждое сообщение людям перед отправкой агент
сверяет глазами по картинке - тот ли чат, тот ли текст, так ли легли строки.

Живая проверка в WhatsApp Web (редактор Lexical) нашла ловушку: после «line1», Shift+Enter, «line2»
в поле два `<p>`, `innerText` поля - «line1\n\nline2», а ушло сообщение с одним переводом строки.
Проверка по `innerText` показала бы модели пустую строку, которой нет.

## Варианты

1. **Только промпт:** сказать в пояснении «переводи строку Shift+Enter, проверяй до Enter».
   Дёшево, но ничего не гарантирует: модель по-прежнему может прислать `\n` с `submit`, а
   инструмент сам решает, какой клавишей стал `\n`. Пояснение к тому же упирается в 2048 знаков.
2. **Вставлять многострочный текст целиком везде** (как было в Browser) и полагаться на
   редактор. Для textarea это верно, для редакторов на contenteditable - лотерея, а у Computer Use
   вставки нет (кроме Windows), там клавиши.
3. **Правило в инструментах (выбрано):** перевод строки в набираемом тексте всегда Shift+Enter
   (Shift+Return), пустая строка - два подряд, голого Enter внутри текста не бывает ни в одном пути
   набора. Многострочный текст вместе с `submit` - отказ до первого действия: «набери без submit,
   проверь поле, потом нажми Enter». Проверка встроена в ответ: Browser после набора в редактор
   (contenteditable - поле ввода чатов) без `submit` возвращает текст поля по строкам и картинку
   поля, Computer Use и так возвращает снимок экрана. Минус - лишний вызов CDP и картинка в
   ответе на каждый набор в редактор, и модель тратит ход на Enter отдельно.

## Решение

Вариант 3: гарантию даёт код, а пояснение только объясняет её модели. Ни одного пути, где `\n`
становится голым Enter: ни набор по клавише, ни вставка по строкам, ни Windows с буфером. Отправка
многострочного сообщения всегда двумя шагами, и между ними у модели на руках то, что увидит
адресат: в Browser - строки поля и его картинка, в Computer Use - снимок.

Как это устроено:

- Общие правила - `main/browser/typed-lines.ts`: `\r\n` и `\r` становятся `\n`, отказ «многострочный
  текст с submit» один на оба коннектора.
- Browser (`page-typing.ts`, `page-actions.ts`): у текста с переводами строк сначала читается поле
  с фокусом (ссылка бывает обёрткой редактора). Редактор и неизвестное поле - строка за строкой
  (короткий текст по клавише, длинный - вставкой каждой строки), между ними Shift+Enter. textarea -
  вставкой целиком: там перевод строки - знак значения, клавиши не нужны (`slowly` - по клавише, тоже
  с Shift+Enter). Однострочное поле - отказ: Chrome сам заменил бы переводы строк пробелами
  («a\nb\n\nc» стало бы «a b c»), и модель не узнала бы об этом. Знак `\n` по клавише
  (`charEvents`) - тоже Shift+Enter.
- Проверка поля (`field-read.ts`): текст редактора собирается по его устройству, а не `innerText`:
  блок (по вычисленному `display`) - строка, `<br>` внутри блока - перевод строки, пустой блок -
  пустая строка, последний `<br>` блока - заглушка Chrome и редакторов, строки не даёт. Картинка -
  `Page.captureScreenshot` по коробке поля с полями 12 px внутри видимой части, длинная сторона до
  1200 точек; не нарисовалась за 5 с - ответ без неё, набор не падает. `fill` отдаёт текст полей
  (`fieldText`) без картинок.
- Computer Use (`computer-hand.ts`): `\n` - Shift+Return (на Windows Shift+Enter) и между вставками
  из буфера тоже, у `type` появился `submit` - Return после однострочного текста. Ответ без
  `submit` напоминает сверить поле по снимку до Return.
- Пояснения обоих серверов получили строку «Messages to people: ...»: пиши абзацами, перевод
  строки - Shift+Enter, до Enter проверь картинку поля (снимок) и чат. Чтобы она влезла в 2048 знаков
  вместе с описанием человека, из пояснений убраны повторы описаний инструментов (open_app, «cmd -
  это Ctrl» на Windows, «настоящие мышь и клавиатура» - это уже говорит первая строка), а правило
  вкладок Browser сказано короче, с теми же условиями.

## Факты и замеры

- Сквозной тест на Chrome for Testing 1248 (временный профиль, своё расширение и host), страница
  `/chat` в `browser.e2e.test.ts`: два редактора, где Enter без Shift «отправляет», - родной
  contenteditable Chrome и подобие Lexical (строка - `<p>`, Shift+Enter - новый абзац). Короткое
  сообщение с пустой строкой (по клавише) и длинное в 7 строк с двумя пустыми (вставкой по строкам):
  до Enter не ушло ничего, текст поля в ответе совпал с сообщением, картинка - поле шириной 400-700
  точек, а не окно в 900; `innerText` подобия Lexical при этом показывал лишнюю пустую строку. После
  Enter ушло ровно одно сообщение с теми же строками. Голых Enter за весь тест - два, оба отправка,
  все 9 переводов строк - с Shift. Многострочный текст с `submit` и в однострочное поле - отказ.
  Прогон 13 с на MacBook Pro M5 Pro:
  `AGENTIC_WORKSTATION_BROWSER_E2E=1 pnpm --filter @agentic-workstation/desktop exec vitest run src/main/browser/browser.e2e.test.ts -t "сообщение в чат"`.
- Там же разово: `Input.insertText` с «a\nb\n\nc» в `<input>` дал значение «a b c».
- Длина пояснений с описанием человека в 1000 знаков (тест `connector-view.test.ts`): Browser 2046,
  Computer Use 1949 на маке и 2043 на Windows при пределе 2048.
- Живьём в WhatsApp, Slack и Teams после изменения не проверялось: инструменты коннекторов
  настоящего Chrome и мака человека в этой работе не трогались.

## Последствия

- Новый путь набора текста в любом из двух коннекторов обязан держать правило: `\n` - только
  Shift+Enter, многострочный текст с `submit` - отказ. Держат тесты `page-typing.test.ts`,
  `page-keys.test.ts`, `computer-hand.test.ts`, `computer-tools.test.ts`, `browser-tools.test.ts`.
- Ответ `type` Browser в редактор - уже не один JSON: шапка, строка с текстом поля и картинка.
- Пояснения обоих серверов заполнены почти до 2048 знаков. Новое правило туда - только за счёт
  сжатия старого, иначе под нож уходит описание человека.
- Пересмотреть, если найдётся мессенджер, где Shift+Enter тоже отправляет или не переносит строку
  (тогда нужна клавиша по сайту), или если картинка поля на каждый набор в редактор окажется
  заметной долей токенов разговора (тогда - только для многострочного текста).
