# 0040. Браузер для ИИ - расширение Chrome по native messaging и встроенный коннектор Browser

- **Статус:** Принято
- **Дата:** 2026-11-10

## Контекст

Владелец хочет, чтобы ИИ из IDE работал в его настоящем Chrome, с его входами на сайтах, и
чтобы это было видно и не мешало: свой курсор агента на странице, вкладки агента в своей
группе, которая в конце очищается и закрывается, человек спокойно работает в других вкладках
или сворачивает браузер. Правой кнопкой на странице можно скопировать ссылку на вкладку и дать
её ИИ. ИИ может открывать пустые вкладки. Стиль - как у IDE.

Решения владельца, которые не обсуждаются: управление через отладчик Chrome
(`chrome.debugger`, CDP) и только на время работы; ИИ видит и может взять все вкладки профиля.

Ограничения, которые нельзя обойти:

- Фирменный Chrome с версии 137 не принимает `--load-extension`, поэтому живая проверка идёт
  на Chrome for Testing из Playwright, а человек ставит расширение кнопкой «Load unpacked».
- Сервис-воркер MV3 засыпает через полминуты тишины. Открытый порт native messaging держит его
  живым (Chrome 105+), открытый WebSocket - нет.
- Шлюз коннекторов берёт порт у системы на каждый запуск (ADR 0028), расширение его не узнает.
- Chrome запускает native host из launchd с пустым PATH: `node` у человека может не найтись.
- Ответ host в Chrome - не больше 1 МБ, в обратную сторону - до 64 МБ.

## Варианты

**Связь расширения с IDE.**

1. WebSocket на localhost. Привычно, но порт пришлось бы закрепить и открыть всем процессам
   машины (и страницам в браузере через DNS rebinding), а сервис-воркер с WebSocket засыпает.
2. Native messaging. Chrome сам запускает host и пускает к нему только расширение из
   `allowed_origins`, порт не открыт никому, сервис-воркер не засыпает, пока порт открыт. Так
   сделаны Claude in Chrome и Codex у владельца. Нужен host и манифест в папке каждого браузера.

**Чем исполнять host.**

1. `node` из PATH - его может не быть, и у Chrome PATH пустой.
2. Собранный бинарник (Node SEA, pkg) - ещё одна сборка, подпись и сотни мегабайт.
3. Бинарник самой IDE с `ELECTRON_RUN_AS_NODE=1` - Node уже внутри, путь известен IDE.

**Где логика действий.**

1. В расширении: клик по элементу, ввод, снимок страницы. Но распакованное расширение
   обновляется только перезагрузкой, а проверить логику без браузера нельзя.
2. В IDE: расширение тонкое - вкладки, группа, сырые команды CDP, курсор и рамка. Клик,
   ввод, снимок, ожидание, сессии - в главном процессе, с тестами без браузера.

**Сессия браузера.**

1. Одна на коннектор. Два разговора делили бы одну группу и одни вкладки.
2. Своя на каждый процесс разговора, по ключу запуска шлюза (ADR 0029). Конец процесса
   закрывает его вкладки сам. Но процесс разговора сменяется посреди работы: новый набор
   коннекторов, другой аккаунт, отложенный перезапуск, сон после простоя - и вкладки агента
   закрывались бы посреди задачи.
3. Своя на разговор (вкладка панели, сессия сценария), процессы разговора её делят. Конец
   процесса не закрывает вкладки сразу, а ждёт следующий процесс того же разговора; закрытая
   вкладка разговора закрывает их сразу.

## Решение

Расширение MV3 (`apps/browser-extension`) говорит с IDE по native messaging. Host
(`apps/desktop/src/native-host/host.ts`) - один файл JS, его исполняет бинарник IDE как Node
через обёртку `sh`; он переводит кадры native messaging в строки JSON по unix-сокету IDE
(`~/.agentic-workstation/browser/<профиль IDE>.sock`, права 600) и переподключается сам, когда
IDE перезапустилась, а без IDE говорит расширению «IDE не запущена». Расширение тонкое, логика -
в главном процессе (`main/browser/`): снимок страницы из дерева доступности со ссылками `e12`,
клики и ввод через `Input.*`, ожидание загрузки, консоль. В IDE это встроенный коннектор
`browser` с сервером `browser-chrome`: инструменты исполняет шлюз, сессия своя у каждого
процесса разговора. Главная причина - native messaging единственный вариант, где связь
закрыта от чужих процессов и не засыпает, а логика в IDE не требует переустанавливать
расширение при каждой правке. Сессия - на разговор (вариант 3): смена процесса разговора -
внутреннее дело IDE, человек её не видит, и вкладки агента не должны от неё пропадать.

Как устроено:

- **Протокол** - пакет `packages/browser-protocol`: сообщения (hello, welcome, запрос, ответ,
  событие), имена host (`com.agentic_workstation.browser` у установленной IDE,
  `com.agentic_workstation.browser_dev` у dev; расширение держит связь с обоими), постоянный id
  расширения из ключа в манифесте (`mdlbfahcfjmnkgbmpfjdppaljimjmknc`), ссылка на вкладку
  `chrome-tab:<профиль>/<id>@<метка запуска> "Заголовок"`, кадры и строки. Метку запуска
  расширение заводит заново на каждом старте Chrome (`runtime.onStartup`) и шлёт в hello: id
  вкладок после перезапуска раздаются заново, и ссылку с другой меткой IDE не принимает, а
  ссылку без метки сверяет по заголовку. id запросов у каждой связи начинаются со случайного
  места, а host пересылает в IDE только ответы на запросы, пришедшие по нынешнему сокету:
  поздний ответ прежней IDE не закроет новый запрос. Сборщики кадров и строк линейные.
- **Установка** - только когда человек добавил или включил коннектор Browser (и на старте IDE,
  если он есть и включён, чтобы после обновления в папке была новая сборка): копия host и
  обёртка в `~/.agentic-workstation/native-host/<канал>`, копия расширения в
  `~/.agentic-workstation/chrome-extension` (путь без пробелов, не меняется между версиями),
  манифест host в `NativeMessagingHosts` каждого установленного браузера семейства Chromium
  (Chrome, Beta, Dev, Canary, Chromium, Brave, Edge, Arc, Vivaldi). Удаление коннектора -
  включённого или выключенного - убирает сокет, манифесты и host, папку расширения не трогает;
  на старте без коннектора то же подчищает остатки прошлых запусков. Отдельный профиль IDE
  (копия окна агента) браузеры человека не трогает, тесты пишут манифесты только в
  `AGENTIC_WORKSTATION_BROWSER_HOSTS_DIR` или в папку профиля своего Chromium. Сокет не влез
  в предел unix-сокета (длинный домашний путь) - он во временной папке пользователя (своя
  папка 700, владелец проверяется), не влез и туда - код сбоя `socket-path` в окне; старт IDE
  от этого не падает. Новую сборку в папке расширение видит по welcome и перезагружает себя
  один раз на сборку.
- **Сессия** - на разговор: процесс получает ключ шлюза, и сразу, до подъёма CLI, его
  называют разговором и папкой работы (`McpLaunch.own`: id вкладки панели и проект, у сессии
  сценария - её id и worktree). Конец процесса отпускает сессию не сразу, а через 10 минут,
  если новый процесс того же разговора не пришёл (`SessionLaunches`); закрытая вкладка
  разговора (`McpLaunch.end`) закрывает её сразу. Вызов процесса, который уже кончился,
  отказывается; вкладка, открытая или взятая, пока сессию заканчивали, сразу закрывается или
  отпускается; открытие вкладки не обрывается отменой посреди пути, отмену проверяет ответ.
  Первая вкладка создаёт оранжевую группу «AW · <проект>» в окне, где человек был последним;
  вкладки открываются неактивными. Взятые по ссылке вкладки остаются на месте с рамкой.
  `finish` закрывает свои вкладки, которые ещё в группе сессии; свою вкладку, которую человек
  вытащил из группы, и взятые - отпускает; чужие вкладки, перетащенные в группу, выводит из
  неё. Закрытую человеком группу сессия не воскрешает. Stop в окне расширения и «Отмена» на
  плашке отладчика Chrome (`canceled_by_user`) - одно и то же: сессия кончается, модель узнаёт
  об этом на следующем вызове. Отладчик подключается на время работы и отключается после
  минуты простоя; две IDE в одной вкладке держат его вместе (расширение отключает его, когда
  отпустила последняя), а «не подключён» в IDE - повод подключиться заново один раз.
- **Профиль отключился** (расширение перезагрузилось, Chrome перезапускается, IDE упала) -
  IDE не забывает вкладки, а помечает их без связи и сверяет по `tabs.list`, когда профиль
  вернулся с той же меткой запуска; с другой - забывает. Расширение помнит свои вкладки и
  группы каждой IDE в `storage.local`: IDE вернулась - первая её сводка сессий закрывает
  вкладки прежних связей, которых в ней нет; не вернулась за минуту - закрывает все её
  вкладки; Chrome стартовал - закрывает восстановленные им группы агента (вкладки по адресам
  агента, остальные выводит из группы).
- **Диалоги страницы** принимаются сами, кроме «Покинуть сайт?» на вкладке человека: там
  агент остаётся на странице, а модель узнаёт с ответом, что надо спросить человека.
- **Курсор и рамка** - скрипт в закрытом shadow DOM страницы, внедряется по требованию;
  значения стиля - токены `packages/ui/src/styles/tokens.css`, сборка расширения вписывает их
  блоком `:root, :host`. Слой - `popover="manual"` в верхнем слое документа и поднимается
  заново на каждой рамке и движении курсора: модальное окно сайта, его popover и полноэкранное
  видео его не закрывают. Рамка помнит, какие IDE её поставили (в `storage.local`), и уходит,
  когда отпустила последняя или её IDE пропала. Токены берут CSS `round()`, поэтому
  расширение - для Chrome 125 и новее (манифест и цель сборки).
- **Фреймы.** Дерево доступности Chrome отдаёт по одному документу: у главного фрейма iframe -
  пустой узел `Iframe`. Фрейм того же процесса читается сессией вкладки
  (`Accessibility.getFullAXTree` с `frameId`), фрейм другого процесса (cross-origin iframe:
  платёжное поле, вход через чужой сайт, виджет) - своей сессией. К таким фреймам расширение
  подключается само вместе с вкладкой (`Target.setAutoAttach` с `flatten` и фильтром `iframe`, у
  каждого нового фрейма - заново, ради вложенных) и держит их сессии в реестре (`ChildTargets`):
  IDE называет фрейм его id (id цели фрейма другого процесса = id фрейма), а не id сессии - сессия
  меняется с каждым подключением отладчика, и ссылки снимка пережили бы отключение после минуты
  простоя только так. Протокол: `debugger.frames` - список таких фреймов, `cdp` с `frame` -
  команда в его сессию, отказ `no-frame` - фрейма больше нет. Снимок собирается уровнями: главный
  документ, потом фреймы, которые попали в текст в пределах 40 тысяч знаков, потом их фреймы - не
  больше 30 фреймов и 5 уровней; фрейм находится по `DOM.describeNode` элемента iframe. В тексте
  фрейм - строка `- iframe "Имя" [ref=e5] [frame=f2]` с его документом под ней, ссылки его
  элементов - `f2e7`; iframe без title подписан заголовком документа; фрейм, который не прочесть
  (ушёл, не ответил за 10 секунд), - просто строка iframe. Команды над узлом (прокрутка, рамки,
  `Runtime.callFunctionOn`, загрузка файла) идут в сессию фрейма, мышь и клавиатура - всегда во
  вкладку: Chrome сам отдаёт ввод фрейму под точкой или в фокусе. Узлы фрейма другого процесса
  отвечают в координатах его окна - к точке прибавляется левый верхний угол содержимого его
  элемента iframe (`DOM.getBoxModel`, без рамки и полей), и так через все фреймы других процессов
  до страницы; перед этим их iframe прокручиваются в видимую часть, от внешнего к внутреннему:
  прокрутка изнутри такого фрейма доходит до страницы через другой процесс уже после ответа.
- **Инструменты** - чтение: `profiles`, `tabs`, `snapshot`, `screenshot`, `console`; запись:
  `open`, `take`, `navigate`, `back`, `forward`, `reload`, `click`, `type`, `fill`, `press`,
  `hover`, `scroll`, `select`, `wait`, `evaluate`, `close_tab`, `finish`; отправка
  (`outbound`, выключена, пока её не включит человек) - `upload`: файл с этой машины уходит на
  сайт, и страница может об этом попросить сама. Загрузка и адреса `file:` - только файлы
  внутри папки разговора (проект, у сценария - его worktree), по настоящему пути после
  ссылок: «Load unpacked» по умолчанию даёт расширению доступ к `file:`. Отдельной ступени
  отправки для клика нет: клик по «Отправить» не отличить от любого клика. Ответы держат
  пределы модели: `tabs` - строка на вкладку с фильтром и «ещё N», `console` - не больше 20
  тысяч знаков, картинка - не больше 2000 пикселей по длинной стороне с учётом Retina (вся
  страница - сверху, не выше двух её ширин, с пометкой), тяжелее 4.5 МБ - JPEG. Дерево
  доступности расширение прореживает (без кусков строк, источников имён, ролей Chrome) и
  обрезает по объёму, а ответ больше 60 МБ становится отказом `too-large`, а не обрывом порта.
  Дата, время, месяц, неделя, цвет и ползунок получают значение напрямую, с проверкой и
  форматом в отказе; ссылки снимка сбрасываются со сменой адреса, пропавший элемент - «возьми
  новый снимок»; ожидание текста ищет его в странице и переживает переход.

## Факты и замеры

Mac на Apple Silicon, macOS 27 (Darwin 27.0.0), Chrome for Testing 158.0.8127.18 (Playwright
`chromium-1254`), Electron 44.7.2.

- Сборщики кадров и строк (20 МБ кусками по 64 КБ): прежние склеивали всё накопленное на
  каждом куске - 1.4 с кадры и 0.8 с строки; линейные - около 25 мс
  (`packages/browser-protocol/src/framing.test.ts`, предел теста 400 мс).
- `Page.captureScreenshot` с `clip`: координаты - от начала документа (`cssVisualViewport.pageX`
  и `pageY`), а не от окна: проверено прокруткой на 1200 пикселей и цветом полосы в сквозном
  тесте при `deviceScaleFactor` 3.
- `--load-extension` работает в Chrome for Testing и без окна (`--headless=new`). Со своей
  папкой профиля Chromium ищет манифесты host в `<папка профиля>/NativeMessagingHosts`.
- Картинка фоновой вкладки (неактивная, за вкладкой человека): `Page.captureScreenshot`
  отвечает за 30-60 мс настоящим содержимым и без окна, и с окном. Пока отладчик подключён,
  страница считает себя видимой (`visibilityState: visible`).
- Свёрнутое окно (`Browser.setWindowBounds` с `minimized`, с окном): картинка за 35 мс с
  настоящим содержимым, клик работает, страница считает себя видимой. Запасной путь из плана
  (отдельное окно агента) не понадобился; на случай, когда картинка не пришла за 15 секунд,
  инструмент отвечает снимком дерева.
- Курсор и рамка видны на картинке: стрелка акцентного цвета у точки клика, рамка
  `--color-accent` по краю. Окно расширения: ряды ровные по вертикали (центры совпадают до 1
  пикселя).
- `open -a <Chrome> chrome://extensions` открывает страницу расширений в запущенном браузере
  (проверено на Chrome for Testing со своей папкой профиля).
- Собранное приложение (`electron-builder --dir`): host и расширение лежат в
  `Contents/Resources`, не в `app.asar`; бинарник приложения с `ELECTRON_RUN_AS_NODE=1`
  исполняет host (Node 24.21.0).
- Фреймы (Chrome for Testing без окна, CDP напрямую и через расширение): `<iframe>` в дереве
  главного фрейма - узел роли `Iframe` без детей с `backendDOMNodeId` элемента;
  `DOM.describeNode` элемента отдаёт `frameId` и для фрейма того же процесса (с
  `contentDocument`), и для фрейма другого процесса (без него). 127.0.0.1 и localhost - разные
  сайты, фрейм с localhost - в своём процессе, и id его цели совпадает с `frameId`. Сессия вкладки
  на `getFullAXTree` с `frameId` такого фрейма отвечает «Frame with the given frameId is not
  found». Фрейм с 127.0.0.1 внутри фрейма с localhost на странице 127.0.0.1 - снова своя цель (о
  ней Chrome сообщает сессии родителя после `setAutoAttach` в ней). Сообщения
  `Target.attachedToTarget` об уже открытых фреймах приходят раньше ответа на `setAutoAttach`.
  Рамки узлов фрейма того же процесса - уже в координатах страницы (кнопка фрейма начинается
  ровно в углу содержимого iframe: 62, 129 при рамке 5 и поле 7), фрейма другого процесса - от
  угла его окна (0, 0). Клик `Input.dispatchMouseEvent` по вкладке в сумме координат попадает в
  кнопку фрейма другого процесса, `Input.insertText` после клика печатает в его поле - и в
  неактивной вкладке. `chrome.debugger.sendCommand` с `sessionId` и `onEvent` с `sessionId`
  работают с сессиями фреймов (Chrome 125+).
- Сквозная проверка: одиннадцать сценариев за 17 секунд - фреймы (снимок с фреймом того же
  процесса, другого процесса и вложенным в него; клик, ввод, `fill`, `select`, `hover`, прокрутка
  к элементу и `evaluate` с элементом во фреймах; фрейм другого процесса ниже первого экрана),
  группа и неактивная вкладка, снимок,
  клик, ввод, выбор, флажок, дата и время, загрузка файла проекта и отказ файлу вне его,
  ожидание через переход страницы, устаревшая ссылка элемента, консоль, картинка, переход и
  назад, `finish`; взятие вкладки человека по ссылке и отпускание; две IDE в одной вкладке;
  конец процесса без разговора; размер картинки на Retina и место прокрутки; обрезанный
  снимок длинной страницы; пиксели картинки фоновой вкладки, курсора и рамки (и свёрнутого
  окна с окном); курсор над модальным окном сайта; окно расширения (связь, сессия, имя
  профиля, ссылка на вкладку, Stop); IDE упала и поднялась без сессий - расширение закрывает
  её вкладки.

## Последствия

- Новые части с границами в `eslint.config.mjs`: `browser-protocol` (импортирует только
  себя), `browser-extension` и `native-host` (себя и протокол); главный процесс видит
  протокол. Host - чистый Node, Electron в нём запрещён линтером.
- `pnpm dev` и `build` сначала собирают расширение; electron-vite кладёт host и расширение в
  `out/native-host` и `out/chrome-extension` рядом с main, electron-builder - в ресурсы
  приложения. Тронул их сборку - проверить упаковку.
- `NativeSource` получает процесс разговора (`NativeCall`: ключ запуска, разговор, проект,
  папка работы) и узнаёт о конце процесса (`release`) и разговора (`endConversation`): этим
  может пользоваться любой встроенный тип, которому нужно своё на разговор. Процессы команд
  остальных типов по-прежнему свои у каждого процесса и гаснут с ним.
- ИИ видит все вкладки подключённого профиля и может выполнить в них любой JS (`evaluate`).
  Ограничить можно коннектором: выключить, оставить только в части проектов, выключить
  инструменты записи. Загрузка файлов на сайт выключена, пока её не включит человек, и даже
  включённая берёт только файлы папки разговора.
- Граница доверия - пользователь macOS, точно так: сокет моста - права 600 в папке 700,
  конфиги шлюза с ключами процессов - права 600 в userData. Любой процесс этого пользователя
  (в том числе Bash самого разговора) может прочесть ключ живого процесса разговора и через
  шлюз водить браузер, или подключиться к сокету под видом расширения и подсунуть IDE ложные
  вкладки. Процессы других пользователей и страницы в браузере - не могут: порта нет, host
  пускает только наше расширение (`allowed_origins`).
- Мост держится на `ELECTRON_RUN_AS_NODE`: host исполняет бинарник IDE как Node. Выключить
  fuse RunAsNode при упрочнении сборки - значит сломать браузер для ИИ; тогда host нужен
  свой исполнитель.
- Пока не сделано: консоль - с момента подключения отладчика и только главного фрейма и
  фреймов его процесса; диалоги страницы (alert, confirm) во фрейме другого процесса агент не
  видит - Chrome показывает их сам, а фрейм ждёт; `evaluate` без элемента - в главном фрейме
  (с элементом - в его фрейме); место повёрнутого или масштабированного трансформом iframe
  другого процесса считается по углу его содержимого, без трансформа; группа называется по
  проекту, а не по разговору.
- Пересмотреть: при публикации в Chrome Web Store (ключ сохранить тем же, копия закрытого
  ключа - `agentic-workstation-extension-key.pem` в корне, вне git), если Chrome перестанет
  рисовать скрытые вкладки для отладчика или отдавать сессии фреймов расширениям.
