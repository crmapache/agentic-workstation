# 0131. Codex спрашивает одобрение вызова инструмента MCP - карточкой разрешения у строки вызова

- **Статус:** Принято
- **Дата:** 2026-11-26

## Контекст

Коннекторы у Codex работали только в режиме «без вопросов». В остальных режимах любой вызов
инструмента коннектора без пометки «только чтение» (открыть страницу в Browser, поиск чата в
chatkepr, у которого пометок нет вовсе) отклонялся за 1-20 мс. Модель получала «user rejected MCP
tool call» и говорила человеку, что он отказал, хотя никакого вопроса он не видел. У Claude те же
коннекторы работали.

Причина в протоколе. Codex 0.163 перед таким вызовом спрашивает клиента формой MCP
(`mcpServer/elicitation/request`, режим `form`, пустая схема) с пометкой
`_meta.codex_approval_kind = "mcp_tool_call"`, вариантами запоминания в `_meta.persist`
(`session`, `always`) и аргументами в `_meta.tool_params`. IDE из этих запросов знала только
вход по ссылке (`mode: url`). На форму она отвечала «Unsupported request», а Codex такой ответ
считает отказом человека. В журнал ничего не писалось, поэтому сбой был немым. Проверка
«незнакомый вопрос - отказ» стояла раньше проверки «в режиме без вопросов принять», так что
форма не прошла бы и там, если бы Codex её прислал.

Вторая разница с Claude: уведомления себе, свои серверы IDE и чтение у сервера `workstation`
Claude получает без вопроса (`--allowedTools` из `GatewayLaunch.allowed`). Codex этих правил не
получал, и после починки спрашивал бы о каждом уведомлении.

## Варианты

**Выдать Codex все серверы шлюза с `default_tools_approval_mode="approve"`.**

- Плюсы: одна строка во флагах, вопросов больше нет.
- Минусы: режимы панели для коннекторов теряют смысл: в «спрашивать» Codex молча нажимает в
  Chrome человека и пишет в его трекер. Claude в тех же режимах спрашивает.

**Показывать форму общим вопросом с вариантами (Allow / Allow for this session / Cancel).**

- Плюсы: разбор формы в вопрос уже есть у ACP.
- Минусы: вопрос не привязан к строке вызова в ленте, а режим «без вопросов» его не принимает
  сам. Человек видит не ту карточку, что у команд и правок Codex и у вызовов Claude.

**Форма одобрения - карточкой разрешения у строки вызова; правила шлюза - флагами одобрения.**

- Плюсы: тот же вид и те же клавиши, что у остальных разрешений. Режим «без вопросов»
  принимает сам, отказ и снятый вопрос уходят как decline. Набор «без вопроса» у Codex и у
  Claude один и берётся из одного места.
- Минусы: id вызова Codex в вопрос не кладёт. Строку приходится искать по серверу,
  инструменту из текста вопроса и аргументам.

## Решение

Третий вариант. Форма с пометкой `mcp_tool_call` становится разрешением (`codex-mcp-approval.ts`).
Оно привязано к идущему вызову того же сервера и инструмента с теми же аргументами, а без такого
вызова - к последнему вызову этого сервера. Строки в ленте нет совсем - вызов собирается из самого
вопроса. «Разрешить и дальше» отвечает `persist: "session"` и показывается, только если Codex
предложил `session`. Вариант `always` IDE не шлёт никогда: Codex пишет его в свой `config.toml`,
а серверов IDE там нет (их дают флаги процесса), так что запись не удалась бы. Правила шлюза
`mcp__<сервер>` и `mcp__<сервер>__<инструмент>` уходят во флаги сервера:
`default_tools_approval_mode="approve"` или `tools.<имя>.approval_mode="approve"`. Незнакомый
запрос сервера по-прежнему получает отказ, но со строкой в журнале: метод, режим формы и пометка
Codex, без аргументов. Главная причина - у Codex и у Claude одни правила, о чём спрашивать
человека, и одна карточка.

## Факты и замеры

- Журналы сессий Codex (`~/.codex/sessions/2026/11`) по разговорам из IDE на 2026-11-26. В
  режиме never прошли 383 вызова без пометки «только чтение». В режимах on-request и untrusted
  отклонены все 9 таких вызовов, и все с «user rejected MCP tool call». Вызовы с пометкой
  «только чтение» прошли во всех режимах.
- Формат вопроса и ответа сверен с исходниками Codex 0.163: `codex-rs/core/src/mcp_tool_call.rs`
  (`build_mcp_tool_approval_elicitation_request`, `parse_mcp_tool_approval_elicitation_response`)
  и `codex-rs/protocol/src/mcp_approval_meta.rs`. Ответ accept с `_meta.persist = "session"` -
  одобрение до конца сессии; accept без него - один раз; decline - «user rejected MCP tool call».
- Флаги одобрения принимает установленный Codex 0.163. Неверное значение он отвергает со
  списком `auto`, `prompt`, `writes`, `approve`:
  `codex -c 'mcp_servers.x={url="http://127.0.0.1:9/mcp", tools={"a"={approval_mode="approve"}}}' mcp get x --json`.
- Тесты на поддельном `codex app-server` - разговор панели (`codex-runtime.test.ts`) и прогон
  (`codex-run-process.test.ts`).

## Последствия

- Разовый вопрос к Codex без человека (служебный ИИ, `askCodexOnce`) идёт с политикой never и
  песочницей только для чтения. В таком сочетании Codex сам не одобряет ничего (код
  `mcp_permission_prompt_is_auto_approved`) и отказывает любому инструменту без пометки
  «только чтение», в том числе чтению из коннектора без пометок, как у chatkepr. Поэтому
  выданные ему инструменты (только чтение проекта или допуск шлюза) теперь одобрены всегда, а
  не только при допуске.
- Новый вид вопроса Codex - сначала его форма из исходников нужной версии и тест на поддельном
  сервере, потом код. Отказ без поддержки виден в журнале строкой `[codex] запрос сервера без
поддержки`.
- Набор «без вопроса» меняется в одном месте (`GatewayHost.planFor`), и Claude, и Codex получают
  его оттуда.
- Пересмотреть, если Codex начнёт класть id вызова в вопрос (тогда искать строку не нужно) или
  научится запоминать одобрение для серверов из флагов процесса.
