# 0066. Worktree очереди: локальные файлы Claude Code и общие папки - ссылками на проект

- **Статус:** Принято
- **Дата:** 2026-11-15

## Контекст

Очередь в своём worktree (ADR 0039) получает из проекта только то, что лежит в git, плюс
копии игнорируемых файлов из `.worktreeinclude`. Без этого списка worktree поднимается
голым. На деле в roas-radar это значит, что сценарий работает без личных правил проекта
(`CLAUDE.local.md`), без локальных настроек и хуков Claude Code (там хук, который не пускает
названия личных инструментов в коммиты и Notion), без журнала решений, куда поставка пишет
записи, и без привязки к Vercel для проверки на проде. Две очереди одного проекта параллельно

- ради чего worktree и заводился - в таком виде идут по разным правилам.

Копия закрывает не всё. Журнал, в который прогон пишет, должен пережить worktree, а копия
пропадает вместе с ним. Разрешение, выданное в worktree, и правка правил посреди очереди
должны попасть в один файл с папкой проекта.

## Варианты

**Только `.worktreeinclude` в каждом проекте, IDE не трогать.**

- Плюсы: ничего нового в коде, формат Claude Code.
- Минусы: локальные файлы Claude Code каждый проект перечисляет сам и забывает; копия журнала
  теряет записи прогона при удалении worktree; общую папку копией не сделать.

**Хук на старте сессии в проекте, который ставит ссылки сам.**

- Плюсы: работает и без IDE.
- Минусы: хук живёт в тех самых локальных настройках, которых в worktree нет, - курица и
  яйцо; повторяется в каждом проекте; ставит ссылки в чужой папке из сессии агента.

**Ссылки ставит IDE при создании worktree: локальные файлы Claude Code всегда, остальное -
по своему списку `.worktreelink`.**

- Плюсы: одно место на все проекты; общее остаётся общим; локальные файлы Claude Code
  приходят без настройки.
- Минусы: свой файл IDE рядом с `.worktreeinclude`; ссылка, которую git не игнорирует, стала
  бы новым файлом в worktree - это надо проверять.

## Решение

Ссылки ставит IDE (`main/git/git-worktree-links.ts`) после копий `.worktreeinclude`.
Всегда - `CLAUDE.local.md` проекта и папок выше до корня репозитория и
`.claude/settings.local.json` проекта: Claude Code читает их там. Дальше - строки
`.worktreelink` из корня репозитория: путь от корня на строку, файл или папка целиком, без
шаблонов, `#` - комментарий; путь наружу или в `.git` не берётся. Путь, названный в обоих
списках, становится ссылкой. Ставится только то, что есть в проекте и что git в worktree
игнорирует как ссылку; папку, которая уже есть в worktree, не заменяем. Путь внутри другого
пути набора отбрасывается, а путь, который через ссылку уходит из worktree, не ставится: иначе
замена «копии» стёрла бы настоящий файл в папке проекта. Сбой не отменяет worktree, причина -
в журнал. Главная причина выбора - общее остаётся общим без настройки в каждом проекте.

## Факты и замеры

Проверено на git 2.50 во временном репозитории (повтор -
`npx vitest run src/main/git/git-worktree-links` в `apps/desktop`):

- шаблон `shared/` со слэшем на конце ссылку `shared` не накрывает: `git status` в worktree
  показывает её как новый файл `?? shared`, а `git check-ignore` её не называет. Шаблон
  `shared` без слэша накрывает и папку, и ссылку. Отсюда проверка игнора в самом worktree, а не
  в проекте: в проекте путь - папка, и git судит его иначе;
- `git worktree remove --force` снимает ссылку на папку и не трогает файлы, на которые она
  указывает; обычное удаление чистого worktree со ссылками тоже проходит - игнорируемые не в
  счёт.

## Последствия

- Очередь в worktree работает по тем же правилам и хукам, что и папка проекта, без настройки.
- Проекту, которому нужно общее (журналы, черновики), хватает строки в `.worktreelink`. Путь
  должен игнорироваться git как файл: шаблон без слэша на конце.
- На Windows папка связывается junction, файл - ссылкой, а без прав на неё - копией с записью
  в журнал.
- Пересмотреть, если Claude Code научит `.worktreeinclude` ссылкам: тогда второй список не
  нужен.
