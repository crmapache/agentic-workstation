# 0061. Переход к определению по ⌘: TypeScript в своём процессе, поднимается по требованию

- **Статус:** Принято
- **Дата:** 2026-11-14

## Контекст

Владелец попросил, как в WebStorm: с зажатым ⌘ переменные и импорты под мышью подчёркиваются
ссылкой, клик ведёт к месту, где имя определено, или в файл импорта; другой файл открывается
вкладкой. Условие - быстро, точно и без постоянной нагрузки на систему; если нагрузка будет
постоянной, её можно выключать в настройках.

Языковых серверов в IDE нет (ADR 0005 обещал их «потом»), а встроенные языковые сервисы Monaco
не подключены. Встроенный переход Monaco (DefinitionProvider) нам не подходит: для подсказки при
наведении он требует, чтобы файл цели уже был моделью в редакторе, а у нас модель есть только у
открытых вкладок.

## Варианты

**Языковой сервер TypeScript (tsserver) на проект.**

- Плюсы: точно во всём, включая члены объектов по типам (`result.kind`).
- Минусы: поднимает весь проект с библиотеками: сотни мегабайт и секунды на старт у больших
  репозиториев, а дальше пересчёт на каждую правку - та самая постоянная нагрузка.

**Свой разбор без компилятора** (регулярные выражения или лёгкий парсер и свои области
видимости).

- Плюсы: почти ничего не весит.
- Минусы: области видимости, всплытие объявлений, деструктуризация, типы и значения с одним именем,
  JSX - всё это пришлось бы писать заново и отлаживать на чужом коде.

**Компилятор TypeScript, но по файлу за раз.** Открытый файл - язык TypeScript без библиотек и
без чтения импортов: на этом уровне он точно знает области видимости. Импорт дальше ведём сами:
путь модуля - разрешение TypeScript с tsconfig проекта, в модуле - экспорт с этим именем, через
реэкспорты.

- Плюсы: точность компилятора там, где она нужна; читается только то, куда ведёт имя; нагрузка
  только пока человек ходит по коду.
- Минусы: члены объектов по типам (`obj.prop`, где тип пришёл из другого файла) не находятся;
  компилятор - 8 МБ кода, его старт заметен.

## Решение

Третий вариант. Это ровно просьба - переменные и импорты, - с точностью компилятора и без
проекта целиком в памяти. Компилятор живёт в отдельном служебном процессе Electron
(utilityProcess): поднимается первым ⌘ + наведением в коде и завершается после пяти минут
простоя. Постоянной нагрузки нет, поэтому настройки «выключить» нет. Процесс, а не поток в
главном процессе: поток после выгрузки оставлял там 70-110 МБ, и с каждым кругом больше (замер
ниже), а завершённый процесс отдаёт системе всё.

## Факты и замеры

MacBook Pro M1 Pro, Electron 44.7.2, собранный процесс (`out/main/chunks/definition-worker-*.js`,
8 МБ). Холодный старт - от запуска процесса до первого ответа, включая разбор файла и модуля цели.

| Файл                                                   | Холодный ответ | Следующие   | Память процесса |
| ------------------------------------------------------ | -------------- | ----------- | --------------- |
| import-chase.ts (70 строк), имя из соседнего модуля    | 260-330 мс     | меньше 1 мс | 71-76 МБ        |
| App.tsx amazing-claude-code (7 743 строки), `useState` | 370-450 мс     | 5-7 мс      | 84-100 МБ       |

- Главный процесс после завершения процесса определений: 28 МБ до и 28 МБ после (phys_footprint).
- Тот же движок потоком worker_threads внутри процесса: пока жив +110 МБ, после выгрузки
  остаётся +73…113 МБ и растёт от круга к кругу - так и отказались от потока.
- Сам TypeScript загружается за 160-180 мс; первый разбор App.tsx - около 116 мс.
- Главный бандл вырос на 8 КБ: компилятор - только в файле процесса.

Как повторить: `pnpm --filter @agentic-workstation/desktop build`, затем в Electron
`utilityProcess.fork(путь к definition-worker)` и вопрос `{ id, job: { file, version, offset, text } }`,
память - `footprint <pid>`. Поведение - `vitest run src/main/definitions` (временный проект с
синонимами tsconfig, реэкспортами, пакетами в node_modules, `export =` и require).

## Последствия

- Главный процесс: `main/definitions/` - движок (`definition-engine.ts`: один файл, языковой
  сервис TypeScript без библиотек), разрешение путей (`module-resolver.ts`: ближайший
  tsconfig/jsconfig, у составного - тот, в чей include входит файл; стили и картинки - файлом),
  поиск экспорта по синтаксису (`export-lookup.ts`: реэкспорты, `export *`, `export =` со
  `declare namespace`, тела `declare module`), процесс и простой (`definition-link.ts`).
- Канал `editor:definition`: текст файла едет раз на версию модели, процесс забыл - ответ
  `needText`. Пути цели - от корня проекта, за проектом - абсолютные (вкладка файла по ссылке).
- Окно: `features/editor/definition-links.ts` - жест как у VS Code (⌘ над именем - ссылка без
  движения мыши, ⌘ с другой клавишей - сочетание, протяжка - выделение), имя без определения
  не спрашивается снова до правки. ⌘B и F12 - то же для имени под кареткой, и пункт «Go to
  Declaration» в меню правой кнопки у кода. Переход - `selectFile` с местом: другой файл
  вкладкой, тот же - каретка к имени.
- Только TypeScript и JavaScript (`.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.cts`, `.mjs`, `.cjs`).
- Не находится: члены объектов, чей тип пришёл из другого файла, и экспорты CommonJS в чужом
  JavaScript (`module.exports`): там ведём в начало модуля. Пересмотреть, если в IDE придут
  языковые серверы (ADR 0005) - тогда переход берётся от них, а этот процесс уходит.
