# 0058. Computer Use на Windows - SendInput и SetCursorPos через koffi, текст вставкой из буфера

- **Статус:** Принято
- **Дата:** 2026-11-13

Дополняет [0057](0057-computer-use.md) и заменяет его пункт «только мак»: стол, рука, пауза,
остановка, снимки и инструменты - те же, своё у Windows только то, что ниже.

## Контекст

IDE собирается и для Windows (ADR 0048), а Computer Use вышел только маковым: ввод через
CoreGraphics, разрешения macOS, `open -a`. Владелец попросил Windows сразу. Первая версия решения
писалась без Windows-машины, по тестам на маке; в тот же день владелец дал ноут с Windows 11, и
живая проверка поменяла способ ввода текста (ниже) и нашла ещё четыре поломки.

Чем Windows отличается для руки:

- точки Electron - логические (DIP), а курсор Windows ставится в пикселях экрана; у соседних
  мониторов масштабы разные;
- разрешений нет, зато ввод обычной программы в приложение, запущенное от администратора, система
  молча выбрасывает (UIPI) и не сообщает об этом ни кодом, ни ошибкой;
- главный модификатор - Ctrl, коды клавиш - свои (VK), у стрелок и Home/End - пометка
  «расширенная клавиша»;
- `open -a` нет; приложения из Microsoft Store не лежат файлами;
- текст знаками Юникода (`KEYEVENTF_UNICODE`) занятое приложение принимает вперемешку: знак,
  пришедший, пока оно разбирает предыдущие, подменяется другим («the quick brown» -
  «rrrrrrrrrown»). Так ведёт себя новый Блокнот Windows 11 - во время проверки орфографии, после
  эмодзи, сразу после открытия вкладки.

## Варианты

**Движение курсора.**

1. `SendInput` с абсолютными координатами (0-65535 по всему виртуальному столу). Одно средство на
   всё, но пересчёт в нормированные единицы теряет пиксель на краях и разных масштабах, а сверка
   «курсор там, куда его поставила рука» (ADR 0057) приняла бы промах за руку человека.
2. `SetCursorPos` в пикселях экрана (`screen.dipToScreenPoint`), кнопки, клавиши и колесо -
   `SendInput`. Точно до пикселя; кнопка нажимается там, где курсор уже стоит.

**Приложения от имени администратора.**

1. Ничего не проверять: модель увидит на снимке, что клик пропал. Но она будет пробовать снова и
   снова, не понимая причины.
2. Перед действием спросить систему: окно в точке (или в фокусе) - процесс - его токен -
   `TokenElevation`; окно от администратора, а IDE - нет: отказ с текстом «оставь шаг человеку».
   Не удалось узнать - действовать (ложный отказ хуже пропавшего клика).

**Запуск приложения по имени.**

1. `start "" имя` в cmd - находит только то, что записано в App Paths, «Google Chrome» по
   такому имени не найдёт.
2. `Get-StartApps` PowerShell. Все приложения «Пуска» с AppID, но это функция модуля
   StartLayout, а политика скриптов Windows по умолчанию (Restricted) модули не грузит: на
   свежей Windows open_app не работал бы никогда.
3. То же, что читает Get-StartApps, напрямую: папка оболочки `shell:AppsFolder` через
   `Shell.Application` одной командой PowerShell (обычной команде политика не мешает), вывод - в
   UTF-8. Запуск - `explorer.exe shell:AppsFolder\<AppID>`, как нажатие в «Пуске».

**Ввод текста.**

1. Знаки Юникода по одному с удержанием и паузой. Не зависит от раскладки человека, но надёжен
   только на медленном темпе (60 мс на знак - текст в 450 знаков полминуты), и то без гарантии:
   приложение может быть занято дольше паузы.
2. То же, но перед каждым знаком ждать, что окно в фокусе разобрало очередь (`SendMessageTimeout`
   с `WM_NULL`). Не помогает: Блокнот разбирает ввод отложенно (TSF), окно отвечает раньше, чем
   знак обработан.
3. Вставка через буфер обмена, Ctrl+V настоящими клавишами. Точно и быстро, как вставил бы
   человек. Цена - трогает буфер человека, и не каждое приложение вставляет по Ctrl+V (игры,
   часть терминалов).

## Решение

Курсор и администратор - варианты 2, запуск - вариант 3, текст - вариант 3 с откатом на
вариант 1; всё через koffi, как и на маке (ADR 0008): `user32` (SendInput,
SetCursorPos, GetCursorPos, GetAsyncKeyState, MapVirtualKeyW, WindowFromPoint), `kernel32` и
`advapi32` (процесс и его токен). Главная причина - точность: рука сверяет каждый шаг с местом
курсора, и пиксельный промах сам по себе прерывал бы действия. Раскладка клавиш выбирается по
системе: имена у модели те же («cmd+c» на Windows - Ctrl+C, «win» и «super» - клавиша Windows).

Текст (`win-clipboard.ts`, рука - `computer-hand.ts`):

- перед вставками буфер человека запоминается со всеми форматами-памятью (текст, HTML, картинка
  DIB, свои форматы приложений) и после набора возвращается, если человек за это время не
  скопировал своё; дескрипторы GDI (`CF_BITMAP` и другие) Windows строит заново из DIB. Буфер не
  запомнить (занят, больше 64 МБ) - буфер не трогается, текст идёт знаками;
- текст кладётся отложенно (delayed rendering): Windows просит его у невидимого окна IDE в момент
  вставки - так рука знает, что вставка принята. Рядом - пометки, по которым история буфера
  (Win+V), облачный буфер и менеджеры буфера текст не берут;
- не принято за секунду - рука ждёт, пока окно в фокусе ответит (зависшее не ждёт), и ещё 150 мс:
  иначе запоздавшая вставка взяла бы уже возвращённый буфер человека. Не принято и тогда - этот
  кусок и всё дальше идёт знаками: удержание 30 мс, пауза 30 мс (короткий текст - ритмом руки);
- перевод строки и табуляция - клавишами Return и Tab между вставками, как у набора на маке:
  модель рассчитывает, что Return в мессенджере отправляет.

Ещё четыре правила, которые до живой проверки нашло ревью (сверка с Win32):

- экран блокировки и защищённый стол UAC: GetCursorPos, SetCursorPos и SendInput там отвечают
  отказом - рука проверяет каждый ответ и говорит модели «экран заблокирован», а не «напечатал»;
- левша (кнопки переставлены): флаги SendInput - физические кнопки, поэтому перед нажатием
  спрашивается SM_SWAPBUTTON;
- колесо - только целыми щелчками по 120: старые приложения доли щелчка не крутят;
- Windows 10 старше 2004 не умеет исключить окно из захвата - там капсула прозрачна на время
  снимка.

## Факты и замеры

Живая проверка 13 ноября 2026: ноут с Windows 11 (русский интерфейс и раскладка, масштаб 125%,
на батарее), установщик из `pnpm dist:win`, вызовы инструментов - клиентом MCP с мака через
туннель SSH к шлюзу IDE, ввод человека изображали программы в его сеансе.

Набор одного текста в 453 знака (латиница, кириллица, эмодзи с оттенком кожи, символы) в новую
вкладку Блокнота, прочитан обратно через UI Automation:

| Способ                                    | Время     | Результат                 |
| ----------------------------------------- | --------- | ------------------------- |
| знаки, удержание 6 мс и пауза 6 мс        | 6,5 с     | каша почти во всём тексте |
| знаки, 16 и 16 мс (так шёл набор в IDE)   | 15,5 с    | 8 расхождений             |
| знаки, ожидание окна (`WM_NULL`) без пауз | 0,3 с     | каша                      |
| знаки, 30 и 30 мс                         | 28,2 с    | верно                     |
| вставка из буфера (рука IDE)              | около 1 с | верно                     |

Ещё через руку IDE, всё верно: короткий текст; 4 строки с табуляцией, пустой строкой и эмодзи;
60 строк, 2519 знаков - 17 с (вставка на строку и Return между ними); вставка в поле ввода самой
IDE. Окно, где Ctrl+V выключен: вставка не принята, 40 знаков с кириллицей и эмодзи ушли знаками
за 8 с. Буфер человека с текстом, HTML, картинкой и своим форматом после набора - байт в байт
тот же (DIB и DIBV5 сверены по MD5), картинка из него вставилась в Paint как была. Стоп из капсулы
посреди вставки 60 строк: оборвалось на целой строке, буфер человека вернулся.

Что ещё нашла живая проверка:

- выпущенные сборки Windows 0.1.x шли без нативного модуля koffi (`@koromix/koffi-win32-x64` pnpm
  на маке не ставил): Computer Use падал на первом действии «Cannot find the native Koffi
  module». Исправлено `supportedArchitectures` в `pnpm-workspace.yaml`; сборку без модуля своей
  системы теперь роняет проверка на `afterPack` (`scripts/check-native.cjs`);
- `koffi.view` (буфер поверх чужой памяти) в главном процессе Electron роняет процесс - память
  буфера обмена копируется `RtlMoveMemory` в свой буфер. Процедура окна на JS (`koffi.register`),
  которую Windows зовёт из цикла сообщений Chromium, работает;
- «Блокнот» по-английски на русской Windows не находился - выбор приложения сверяет и AppID;
  запуск через `explorer.exe` со скрытым окном передавал скрытость приложению - Блокнот работал
  без окна;
- клик точен при масштабе 125%; сочетания (cmd+a - Ctrl+A, alt+f4) без залипших модификаторов;
  колесо целыми щелчками крутит Блокнот; перетаскивание окна; капсула - поверх всех, без фокуса,
  вне панели задач и вне захвата экрана, по центру над панелью задач; пауза, стоп, ожидание и
  обрыв при движении мыши человеком; окно от администратора (regedit) - отказ на клик, набор,
  клавишу и колесо.

Не проверено вживую: экран блокировки и запрос UAC, мониторы с разным масштабом, Windows 10
старше 2004, история буфера Win+V (на ноуте выключена - пометки «не в историю» проверены только
тестом), приложение, зависшее посреди вставки.

Повторить тесты: `pnpm --filter @agentic-workstation/desktop exec vitest run src/main/computer`.

## Последствия

- `main/computer/win-native.ts` (объявления вызовов Windows), `win-input.ts` (драйвер поверх
  них, проверяется на подставных вызовах), `win-inputs.ts` (сборка событий, колесо),
  `win-clipboard.ts` и `win-clipboard-native.ts` (буфер обмена и окно-владелец),
  `win-structs.ts`, `computer-keys-windows.constants.ts`, `computer-apps.ts` (open_app обеих
  систем), `capsule-capture.ts`. Рука получает раскладку системы и спрашивает драйвер, примет ли окно ввод
  (`canReach`, у мака его нет). Код отказа - `blocked`.
- Состояние Computer несёт `needsPermissions`: на Windows вместо разрешений окно коннектора
  объясняет запрет UIPI. Коннектор в каталоге на обеих системах.
- Капсула на Windows - окно типа toolbar (нет на панели задач и в Alt+Tab), из захвата экрана её
  убирает `setContentProtection` (WDA_EXCLUDEFROMCAPTURE, Windows 10 2004+).
- Человек на Windows видит в окне коннектора, что текст идёт вставкой и буфер возвращается.
- Сборка любой системы падает, если в ней нет нативного модуля koffi этой системы.
