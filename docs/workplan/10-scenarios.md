# Часть 1. Сценарии на уровне IDE

Требования - раздел «Сценарии» в [PLAN.md](../../PLAN.md), решения владельца - в
[README.md](README.md). Прошлые записи: ADR 0014 (сценарии убраны из панели до переезда на
уровень IDE), ADR 0015 (место в окне - вид середины «Scenarios»).

## Что просил владелец, по пунктам

1. Сценарии - на уровне IDE, а не провайдера → свой сервис `main/scenarios/`, вид середины
   `features/scenarios`, провайдер - только исполнитель.
2. При старте выбирается провайдер (пока только Claude Code) → поле «Provider» в окне запуска,
   у каждого элемента очереди свой провайдер.
3. Галочка «в отдельном worktree» - на запуске, а не в сценарии → на создании ветки (решение
   владельца: worktree на ветку целиком).
4. Несколько веток параллельно, у каждой своя очередь → сущность «ветка сценариев», в
   интерфейсе **Queue** (см. «Слова»).
5. Имя ветки даёт ИИ по содержимому, человек может переименовать.
6. «Остановить после завершения текущего сценария».
7. «Остановить после завершения конкретного сценария».
8. (в PLAN.md второй пункт 7) Страница, где видны все запущенные очереди → вкладка «All
   queues» - доска по всем открытым проектам.
9. Стиль проекта, переиспользование компонентов и токенов.

Плюс «намного более расширенная версия, чем в ACC» - значит, всё, что было в ACC и в архивном
переносе, остаётся: полки, редактор, написание сценария с ИИ, «голова», вопросы человеку,
расписание, продолжение упавшего прогона, смена аккаунта на лимите, журнал шага.

## Слова

| Слово в плане   | В интерфейсе (англ.)                        | В коде          | Что это                                                                                               |
| --------------- | ------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------- |
| Сценарий        | Scenario                                    | `Scenario`      | Описание работы (JSON на полке): этапы, карточки, вводы, настройки головы. Формат ACC.                |
| Полка           | Library: In this project / In every project | `ScenarioScope` | `<проект>/.claude/scenarios/` и `~/.claude/scenarios/`.                                               |
| Ветка сценариев | Queue                                       | `ScenarioQueue` | Именованная линия работы: своя очередь, своя папка (проект или worktree), свой провайдер у элементов. |
| Элемент очереди | Queue item                                  | `QueueItem`     | Один сценарий с ответами на вводы, ждёт, идёт или прошёл в этой ветке.                                |
| Прогон          | Run                                         | `ScenarioRun`   | Одно исполнение сценария движком: голова, шаги, заметки, стоимость.                                   |
| Голова          | Main thread                                 | head            | Сессия агента без права писать, ведёт прогон и судит шаги (как в ACC).                                |
| Карточка / шаг  | Card / Step                                 | card / step     | Карточка - в сценарии, шаг - карточка в прогоне (с повтором и элементом списка).                      |

Почему «Queue», а не «Branch»: у ветки с worktree есть ещё и git-ветка, два «branch» в одном
окне путают. Владелец сам называет страницу «все запущенные очереди». Если утром захочет
«Branch» - это правка строк i18n, не кода. Записано в «Вопросы на утро».

## Формат сценария и полки - как в ACC, без изменений

У владельца уже есть сценарии этого формата: 6 в roas-radar, 2 в claude-code-ide. Значит,
формат и место те же, и они работают сразу, а ACC и IDE читают одни полки.

- JSON `<id>.json`, поля - `shared/claude-scenarios.ts` архива (version 1, id, name, inputs,
  head, stages, cards). `scope` в файл не пишется. Порядок полки - `.order.json`.
- Полки: проект - `<проект>/.claude/scenarios/`, личная - `~/.claude/scenarios/`.
- Правила и проверки - `shared/claude-scenario-rules.ts` архива, переносятся как есть
  (переименовать в `shared/scenario-rules.ts`: они не про Claude).
- Модель и усилие в карточке - строки провайдера. Провайдер при запуске один на элемент
  очереди; модель карточки, которой у провайдера нет, - ошибка запуска с понятной причиной.

Очереди и прогоны ACC (`~/.amazing-claude-code/scenario-*`) не читаем и не переносим: там одна
очередь на проект и другая модель, а прогоны - история другого приложения.

## Провайдеры - `main/providers/`

Сейчас слоя провайдеров нет (`ClaudeService` - всё про Claude, в окне реестр
`workbench/views/provider-views.ts` с одной записью). Делаем узкий слой для нового кода:

```
ProviderId = 'claude'
ProviderInfo { id, label, available: boolean, unavailableReason?, models: {id,label}[] }
AgentSessions {          // для движков: сценарии, позже Remote
  open(opts: { cwd, originProject, sessionId?, resume?, model?, effort?, permissionMode,
               briefing, role: 'head' | 'card' }): AgentSession
}
AgentSession {
  id                                  // id сессии провайдера (для журнала шага, продолжения)
  send(text, images?)                 // ход
  respond(askId, decision)            // ответ на вопрос-разрешение
  interrupt(), close()
  events: turnStarted, said(delta), turnEnded({ text, endings, cost, tokens, error? }),
          asked(Ask), limit(RateLimit), exited(code)
}
ProviderTitles { suggestTitle(text): Promise<string | null> }   // имя ветки
```

- Реализация Claude - `main/providers/claude/`: на `CliProcess`, `cli-args`, разборе потока из
  `main/claude/` и движковом `scenario-session.ts` архива. Тут же Claude-только: аккаунты и
  выручка на лимите (`engine-accounts`, `limit-relief` архива), книжка скрытых разговоров,
  журнал шага из транскрипта (`ConversationFeedSync`).
- Сессии сценариев получают коннекторы IDE так же, как панель: `--strict-mcp-config
--mcp-config` от шлюза, ключ запуска - на **исходный проект** (доступность коннекторов по
  проектам считается по нему, а не по пути worktree).
- Окно получает список провайдеров каналом `providers:list`. Выбор провайдера - общий
  компонент в `features/scenarios` (пока нужен только там).
- Решение «слой провайдеров узкий, ClaudeService не переделываем» - в ADR части.

## Модель данных

```
ScenarioQueue {
  id, projectPath,                       // исходный проект
  name, nameSource: 'ai' | 'user' | 'fallback',
  createdAt, closedAt?,
  workdir: { kind: 'project' }
         | { kind: 'worktree', path, gitBranch, baseCommit, removedAt? },
  items: QueueItem[],                    // по порядку: прошедшие, идущий, ждущие
  stopAfterItemId: string | null,        // «остановить после» (текущего или выбранного)
  hold: null | { reason: 'stopAfter' | 'failed' | 'refused', itemId, at },
}
QueueItem {
  id, scenarioId, scope, scenarioName, inputs, provider: ProviderId,
  afterSuccess: boolean,                 // ждать успеха предыдущего (как в ACC)
  addedAt, runId?: string,
  state: 'waiting' | 'running' | 'done' | 'failed' | 'stopped' | 'skipped',
  refusal?: string,                      // почему не стартовал
}
```

- Прогон (`ScenarioRun`, `RunSummary`, шаги, заметки) - из `shared/claude-scenario-runs.ts`
  архива, плюс `queueId`, `itemId`, `provider`, `cwd`.
- «Остановить после текущего» = `stopAfterItemId` на идущем элементе. «После выбранного» -
  на любом ждущем. Одна сущность, две кнопки. Метка видна на элементе (⏹ после).
- Когда элемент с меткой кончился (любым исходом) - очередь встаёт: `hold.reason='stopAfter'`,
  метка снимается. «Resume» снимает остановку и берёт следующий.
- Пауза (сразу, как сейчас в ACC) остаётся - это пауза идущего прогона: процессы живы,
  продолжает с места. Остановка-после и пауза независимы.

### Где хранится (userData, всё через `storage/json-file.ts`, атомарно)

- `scenarios/<ключ проекта>/queues.json` - очереди проекта (ключ - sha256 пути, 16 знаков).
- `scenarios/<ключ>/runs/<runId>/run.json` + `summary.json` - как в архиве.
- `scenarios/<ключ>/schedules.json` - расписание.
- `scenarios/claude-hidden.json` - книжка скрытых разговоров Claude (сессии сценариев не
  показываются в истории и поиске панели).
- Блокировки файлов - `locked-file.ts` архива: очередь и ACC-подобные места пишутся под
  замком, потому что IDE dev и установленная могут жить одновременно. Владение очередью
  (`ownerPid`) - чтобы два экземпляра IDE не исполняли одну и ту же очередь.

## Движок и очереди - `main/scenarios/`

- `engine/` - движок архива (`engine-*`, `head-*`, `run-*`, `stream-reading`), с заменой
  Claude-связей на `AgentSessions`. Логику не переписывать: она проверена тестами на `FakeCli`
  и повторяет ACC. Переносить вместе с тестами, тесты зелёные до любых правок.
- `queues/` - вместо одной очереди проекта (`queue-rules`, `desk-queue`): очереди-ветки.
  Чистые правила `queue-rules.ts` (что делать очереди сейчас: стоять, взять следующий,
  встать на остановке, встать на провале `afterSuccess`) - с тестами на каждую ветку правила.
  Очереди независимы, параллельно идут сколько угодно. Две очереди без worktree в одной папке
  проекта можно, но окно запуска предупреждает: «в этой папке уже идёт очередь X».
- Прогон вне очереди («Run now» из библиотеки) - это новая очередь из одного элемента. Так нет
  второго пути запуска, и всё видно на одной доске.
- Старт очереди с worktree: сначала worktree, потом прогон. Не создался - элемент `refused` с
  причиной, очередь стоит, worktree не остаётся наполовину.
- Конец очереди (пусто и ничего не идёт) - очередь «idle», не исчезает. Человек закрывает её
  («Close»), закрытая уходит в историю. У закрытой с worktree - вопрос про worktree.
- Выход из IDE: идущие прогоны пишутся `stopped` (как в архиве), очередь при следующем старте
  стоит с `hold`, чтобы ничего не стартовало само без человека. Упавшая IDE: прогон -
  `failed/crashed` по последней записи (как в архиве).
- Расписание (`desk-hours`, `schedule-clock` архива): в назначенный час создаёт **новую
  очередь** с этим сценарием; галочка worktree и провайдер хранятся в записи расписания.
- Написание сценария с ИИ (`author/` архива) - через провайдера, сейчас Claude; модель не ниже
  Sonnet, как было.
- Уведомления ОС (вопрос человеку, конец прогона, остановка очереди) - как в архиве.

### Worktree - `main/git/git-worktree.ts`

- Папка: `~/.agentic-workstation/worktrees/<имя проекта>-<хеш 8>/<slug>`. Без пробелов в пути
  (часть инструментов их не любит), вне проекта (иначе vitest и eslint проекта подхватят копии).
- Git-ветка: `scenarios/<slug>`, slug - из имени первого сценария и 4 знаков id; занята -
  следующий номер. Основа - текущий HEAD исходного проекта (`git worktree add -b`). Незакоммиченное
  в проекте в worktree не попадает - окно запуска говорит об этом, если в проекте есть изменения.
- `.worktreeinclude` (формат Claude Code): если файл есть в корне проекта, перечисленные в нём
  игнорируемые git файлы (`.env` и т.п.) копируются в новый worktree. Зависимости (`node_modules`)
  не копируются - агент ставит сам.
- Удаление: `git worktree remove` (с `--force` только после вопроса человеку, если есть
  несохранённые изменения), git-ветка удаляется, только если она слита или человек подтвердил.
- Сам удаляется после конца очереди, если нет ни коммитов поверх основы, ни изменений.
- Записывающие команды - через `git-write-queue` по корню репозитория. Тесты - на временных
  репозиториях, как `git.integration.test.ts`.
- «Open as project» - открывает папку worktree вкладкой проекта обычным путём workspace.

### Имя очереди от ИИ

- Сразу при создании - запасное имя (имя сценария и первый ответ, как `answerLabel` архива),
  `nameSource='fallback'`. Параллельно - вопрос модели провайдера (Claude: дешёвая модель,
  `structured-ask.ts`, схема `{title}`): «назови работу 2-5 словами» по именам сценариев и
  ответам на вводы. Пришло - `nameSource='ai'`.
- Добавили элемент, а имя не от человека - имя спрашивается заново.
- Переименование человеком - `nameSource='user'`, ИИ больше не трогает. Пустое имя возвращает ИИ.
- Модель не ответила - остаётся запасное, без ошибок в окне.

## Окно - `features/scenarios`

Вид середины «Scenarios» (уже в реестре `main-views.ts`, сейчас заглушка). Раскладка - по ADR
0030: шапка вида (`PageHeader`), разделы (`Section`), подробности предмета - окном по центру
(`Modal`). Пояснения - за кнопкой «?» в шапке, не абзацами (память владельца).

- **Шапка:** «Scenarios», кнопки «Run scenario» (главная) и «New scenario».
- **Вкладки** (`Tabs` со счётчиками): Queues (по умолчанию), All queues, Library, Schedule,
  History.
- **Queues** - очереди текущего проекта, каждая - карточка-полоса:
  - заголовок: имя (переименование по двойному клику и из меню), провайдер, папка (бейдж
    «worktree · scenarios/x» или «project folder»), состояние (`Badge`);
  - дорожка элементов: прошедшие (итог), идущий (стадия, дорожка шагов как `ScenarioRoadmap`
    архива, время, токены, цена, строка «спрашивает»), ждущие; метка ⏹ у элемента с остановкой;
  - кнопки: Pause / Resume (сразу), «Stop after current», «Add scenario»; меню: Rename, Stop
    after… (выбор элемента), Open worktree as project, Remove worktree, Close queue; у ждущего
    элемента - вверх, вниз, убрать, «после успеха / после любого», «Stop after this»;
  - полоса «остановлена: почему» с действием, как баннер очереди архива.
- **All queues** - доска всех очередей всех открытых проектов, сгруппированная по проекту:
  компактные полосы (имя, проект, папка, элементы точками-состояниями, идущий с прогрессом).
  Нажатие - переход на проект и его очередь. Это пункт «страница, где видны все очереди».
- **Library** - полки «In this project» / «In every project», строки сценариев с фактами и
  проблемами, действия: Run, Add to queue, Schedule, Duplicate, Delete, открыть в редакторе.
  Перетаскивание между полками - как в архиве.
- **Schedule** - расписание по дням, как в архиве.
- **History** - прошедшие прогоны таблицей (Run, Queue, Started, Took, Cost, State), звезда,
  удаление.
- **Окно запуска** (`Modal md`): сценарий, ответы на вводы, провайдер, куда - «New queue»
  (галочка «Run in a separate worktree», предупреждение про незакоммиченное) или существующая
  очередь проекта (выбор), «после успеха / после любого».
- **Прогон** (`Modal lg`): шапка с Pause/Resume/Stop/Continue, строка цифр, лента стадий и шагов
  (`ScenarioRunTimeline` архива), карточка вопроса (Allow / Refuse / ответ), поле «написать
  голове», журнал шага.
- **Журнал шага** - разговор провайдера той же лентой, что в его панели. Фича не видит соседнюю
  (`features/claude-code`), поэтому компонент ленты для журнала даёт `workbench` через
  контекст в `state/` (реестр провайдеров уже в workbench). «Continue in a chat» открывает
  разговор головы вкладкой панели провайдера.
- **Редактор сценария** - перенос архива (`Modal lg` или страница вида - по месту; если
  страницей, отдельный ADR-пункт «почему не окно»).
- **Значок на иконке вида** в полосе зоны 8: число прогонов, которые ждут человека.

Компоненты архива (`ScenarioRoadmap`, `ScenarioStatePill`, `ScenarioRunTimeline`,
`ScenarioShelves`, `ScenarioOverlayCard`, формы) - основа, но на текущих примитивах и токенах
(`@agentic-workstation/ui/*`, в архиве ещё `@amazing-ide/ui`). Своих плашек и кнопок рядом с
готовыми не делать (ступени `.claude/rules/design-system.md`). Новый примитив - только при
новой семантике, тогда сразу README пакета и витрина.

## IPC - новая область `shared/ipc/scenarios.contract.ts`

Каналы (имена ориентировочные, итог - в коде):

- Полки: `scenarios:list`, `scenarios:fetch`, `scenarios:save`, `scenarios:delete`,
  `scenarios:duplicate`, `scenarios:place`, `scenarios:draft`, `scenarios:cancelDraft`.
- Очереди: `scenarios:queues` (все очереди всех открытых проектов), `scenarios:start` (новая
  очередь или в существующую), `scenarios:queueItem` (вверх, вниз, убрать, режим),
  `scenarios:stopAfter`, `scenarios:resume`, `scenarios:rename`, `scenarios:close`,
  `scenarios:worktree` (open, remove).
- Прогоны: `scenarios:run`, `scenarios:runs` (история), `scenarios:control` (pause, resume,
  stop, continue), `scenarios:answer`, `scenarios:tell`, `scenarios:stepLog`, `scenarios:star`,
  `scenarios:deleteRun`.
- Расписание: `scenarios:schedule`, `scenarios:unschedule`.
- Провайдеры: `providers:list`.
- События: `scenarios:queues` (снимок очередей), `scenarios:run` (живой прогон, такт 250 мс как
  в архиве), `scenarios:shelves`.

Все команды - методы `ScenarioService`, а не логика в обработчиках: Remote позже позовёт те же
методы.
